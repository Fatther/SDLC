# ADR-001: Модульный монолит Spring Boot с PostgreSQL

## Контекст и постановка задачи

SRS задаёт Java 21, Spring Boot, PostgreSQL, сервер 2 vCPU и 2 ГБ ОЗУ, нулевой бюджет на лицензии и размещение (SRS 2.3, 3.5.7). Работу ведёт один основной разработчик. Какую структуру приложения выбрать, чтобы уложиться в эти ограничения и обеспечить REQ-PERF-001…004?

## Драйверы решения

* Ограничение ресурсов сервера: 2 ГБ ОЗУ, куча JVM не более 1 ГБ (REQ-PERF-004).
* Одна команда и срок до 11.12.2026.
* Простая установка командой `docker compose up` (REQ-INST-001).
* Транзакционная согласованность алертов, истории и товаров (REQ-REL-002).

## Рассмотренные варианты

* Модульный монолит
* Микросервисы
* Два приложения: сервер и фоновый обработчик

## Итог решения

Выбранный вариант: «Модульный монолит», потому что единственный вариант, при котором приложение, фоновые задачи и API укладываются в 1 ГБ кучи на одном сервере и работают в одной транзакционной границе БД. Модули (`account`, `wishlist`, `price-api`, `monitor`, `alerts`, `advisor`, `discounts`, `planner`, `sharing`, `admin`) разделены пакетами и собираются в один JAR.

### Последствия

* Хорошо, потому что один артефакт, одна база и простые интеграционные тесты.
* Хорошо, потому что модуль `advisor` не зависит от Spring и пригоден для повторного использования.
* Плохо, потому что все модули выпускаются вместе, независимое масштабирование невозможно.
* Плохо, потому что границы модулей поддерживаются дисциплиной и тестами, а не процессами.

### Подтверждение

Архитектурный тест ArchUnit проверяет правила зависимостей из SDD (представление 003-dependency). Команда `mvn package` создаёт один исполняемый JAR; CI выполняет тест на каждый pull-request.

## Плюсы и минусы вариантов

### Модульный монолит

* Хорошо, потому что укладывается в 2 ГБ ОЗУ.
* Хорошо, потому что транзакции между модулями без распределённых протоколов.
* Плохо, потому что связанный выпуск всех модулей.

### Микросервисы

* Хорошо, потому что независимые релизы и масштабирование.
* Плохо, потому что несколько JVM не помещаются в 2 ГБ ОЗУ.
* Плохо, потому что распределённые транзакции для алертов и истории.

### Два приложения: сервер и фоновый обработчик

* Хорошо, потому что изоляция тяжёлых проверок от web-запросов.
* Нейтрально, потому что требует общего хранилища и двух образов.
* Плохо, потому что две JVM занимают больше памяти без заметной пользы в масштабе 100 пользователей.

## Дополнительная информация

Связанные документы: [SDD, разделы 2 и 3](../sdd/sdd.md#3-проектные-представления), [SRS](../srs/srs.md). Решение пересматривается, если нагрузка превысит 1000 одновременных пользователей или потребуется независимый выпуск модулей.
