# ADR-002: Клиентская часть — SPA поверх REST API

## Контекст и постановка задачи

REQ-INT-006 требует REST API, через который выполнимы все операции интерфейса. В SRS (раздел 5.1) выбор технологии клиента оставлен открытым. Как построить интерфейс, чтобы не дублировать логику между страницами и API?

## Драйверы решения

* Все операции интерфейса выполнимы через API (REQ-INT-006).
* Адаптивная вёрстка 360–1920 px, светлая и тёмная темы (REQ-INT-001/002).
* Один JAR для развёртывания (ADR-001).
* Ограниченное время на интерфейс (F-11, 12 ч).

## Рассмотренные варианты

* SPA (React) поверх REST API
* Серверные шаблоны (Thymeleaf)
* Серверные шаблоны с htmx

## Итог решения

Выбранный вариант: «SPA (React) поверх REST API», потому что интерфейс использует тот же API, что и внешние клиенты, поэтому REQ-INT-006 выполняется по построению. Собранная SPA кладётся в статические ресурсы JAR и отдаётся Spring Boot.

### Последствия

* Хорошо, потому что нет второго набора контроллеров для HTML.
* Хорошо, потому что темы и адаптивность реализуются на клиенте.
* Плохо, потому что в проект добавляется Node-сборка (подключается плагином Maven).
* Плохо, потому что страница публичного списка требует отдельной лёгкой серверной отрисовки или SPA-маршрута.

### Подтверждение

CI собирает клиент и сервер одной командой Maven; тест OpenAPI проверяет, что каждая операция интерфейса присутствует в `/v3/api-docs`.

## Плюсы и минусы вариантов

### SPA (React) поверх REST API

* Хорошо, потому что единый контракт.
* Плохо, потому что дополнительная сборка и зависимости.

### Серверные шаблоны (Thymeleaf)

* Хорошо, потому что одна технология и простая сборка.
* Плохо, потому что для REQ-INT-006 всё равно нужен отдельный REST-слой, логика дублируется.

### Серверные шаблоны с htmx

* Хорошо, потому что мало JavaScript.
* Плохо, потому что фрагменты HTML не заменяют REST API; дублирование сохраняется.
