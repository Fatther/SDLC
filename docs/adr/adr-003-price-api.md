# ADR-003: Price API как отдельный модуль с фасадом и адаптерами

## Контекст и постановка задачи

При проектировании выяснилось, что SRS 0.1 описывает извлечение цен со страниц (REQ-INT-005), но не требует собственного интерфейса получения цен. Без него добавление товара и периодическая проверка могли бы разбирать страницы напрямую, дублируя контроль robots.txt, ограничения частоты и защиты от SSRF. Как организовать получение цен?

## Драйверы решения

* Соблюдение robots.txt и 1 запроса в 2 с на домен (REQ-COMP-001).
* Защита от SSRF (REQ-SEC-004) и доступ только для доверенных клиентов (REQ-SEC-006).
* Новый магазин без изменения ядра (REQ-MAINT-001).
* Собственный API получения цен (REQ-INT-009), кэш (REQ-PERF-005).

## Рассмотренные варианты

* Прямой разбор страниц в сервисах
* Модуль Price API внутри монолита
* Отдельный микросервис Price API

## Итог решения

Выбранный вариант: «Модуль Price API внутри монолита», потому что все обращения к магазинам проходят через одну точку, где применяются robots.txt, ограничение частоты, SSRF-защита и кэш, и при этом не нужна вторая JVM. Модуль предоставляет два входа: Java-интерфейс `PriceApiClient` для сервисов `wishlist` и `monitor` и REST-маршрут `POST /internal/v1/prices/fetch` с сервисным ключом для доверенных клиентов и тестов. Адаптеры магазинов реализуют `PriceSource`; для магазинов с JSON-LD используется общий адаптер.

### Последствия

* Хорошо, потому что правила вежливого сбора данных реализованы один раз.
* Хорошо, потому что замена магазина затрагивает только адаптер.
* Плохо, потому что падение модуля влияет на добавление и проверку товаров, поэтому ошибки изолируются по магазину (REQ-REL-001).
* Плохо, потому что в SRS добавляются REQ-INT-009, REQ-SEC-006 и REQ-PERF-005, а оценка F-03 составляет 30–36 ч.

### Подтверждение

Архитектурный тест запрещает HTTP-клиенту магазинов использоваться вне пакета `price-api`. Интеграционный тест на 30 страницах трёх магазинов проверяет REQ-INT-009; тест без ключа возвращает 401; запрос к `/internal/**` через прокси отклоняется.

## Плюсы и минусы вариантов

### Прямой разбор страниц в сервисах

* Хорошо, потому что меньше кода на старте.
* Плохо, потому что правила COMP-001 и SEC-004 дублируются в нескольких местах.

### Модуль Price API внутри монолита

* Хорошо, потому что единая точка контроля и простое развёртывание.
* Нейтрально, потому что REST-вход используется в основном вне процесса.
* Плохо, потому что модуль нужно поддерживать как самостоятельный контракт.

### Отдельный микросервис Price API

* Хорошо, потому что изоляция сбоев и независимое масштабирование.
* Плохо, потому что вторая JVM не помещается в 2 ГБ ОЗУ вместе с БД.

## Дополнительная информация

Связанные документы: [SDD 004, 006, 007](../sdd/sdd.md#006-interface), [SRS](../srs/srs.md). Решение пересматривается, если число магазинов превысит 10 или сбор цен потребует отдельного масштабирования.
