## 1. Введение

Документ задаёт требования к веб-приложению PriceRadar — агрегатору скидок и умному планировщику покупок. Он описывает, ЧТО система должна делать, а не КАК это будет реализовано, и адресован заказчику, разработчикам и тестировщикам проекта.

### 1.1 Назначение документа

Спецификация требований к ПО (SRS) фиксирует согласованный с заказчиком набор бизнес-, функциональных и нефункциональных требований к PriceRadar версии 0.1. Заказчик использует её для проверки полноты ожиданий, разработчики — как основу проектирования и реализации, тестировщики — для подготовки тестов по критериям приёмки. Документ поддерживается в репозитории проекта под контролем версий.

### 1.2 Область применения продукта

PriceRadar — web-приложение для людей, которые планируют покупки в интернет-магазинах и хотят платить меньше. Пользователь добавляет товары в вишлист по ссылке, а система регулярно проверяет цены, ведёт их историю, присылает алерты о скидках и рассчитывает оптимальное время покупки («купить сейчас» или «подождать») с объяснением. Цель продукта — сократить переплату за покупки и избавить пользователя от ручного мониторинга цен.

В область релиза входят: учётные записи; вишлист и списки; автоматическое отслеживание цен и история; алерты (в приложении, email, Telegram); лента скидок пользователя; рекомендации по времени покупки; план покупок под месячный бюджет. Вне области текущего релиза: общедоступный каталог скидок по всем товарам магазинов, мобильные приложения, автоматическая покупка и оплата, сопоставление одинаковых товаров в разных магазинах, расширение для браузера.

### 1.3 Определения, акронимы и сокращения

| Термин | Определение |
|---|---|
| Адаптер магазина | Модуль, который извлекает данные о товаре со страниц конкретного магазина и реализует интерфейс PriceSource |
| Алерт | Уведомление пользователя о событии по товару (достигнута целевая цена, снижение цены, появление в наличии) |
| API | Application Programming Interface — программный интерфейс приложения |
| BYN | Белорусский рубль — валюта отображения цен по умолчанию |

| MoSCoW | Метод приоритизации: M (Must) — обязательно, S (Should) — желательно, C (Could) — возможно, W (Won't) — не в этом релизе |
| SRS | Software Requirements Specification — спецификация требований к ПО |
| SSRF | Server-Side Request Forgery — атака, при которой сервер вынуждают обращаться по подставленному адресу |
| Вишлист | Список товаров, за ценой которых пользователь следит |
| Медиана цены | Средняя по порядку цена за выбранный период; устойчива к разовым выбросам |

| Фиктивная скидка | Снижение цены до обычного уровня после предварительного искусственного повышения |

## 2. Обзор продукта

### 2.1 Перспектива продукта

PriceRadar — новый самостоятельный продукт. Он работает как web-приложение на сервере, хранит данные в собственной базе PostgreSQL и обращается к публичным страницам интернет-магазинов, к почтовому SMTP-серверу и к Telegram Bot API. Владелец продукта — автор проекта; SLA не предусмотрен.

```
Пользователь ──► Web-интерфейс ──► Сервер PriceRadar ──► База данных (PostgreSQL)
                                        │
                                        ├──► Страницы магазинов (HTTP/HTTPS)
                                        ├──► SMTP-сервер (email)
                                        └──► Telegram Bot API
```

### 2.2 Функции продукта

- Учётные записи пользователей и вход по email и паролю.
- Вишлист: добавление товара по ссылке, целевая цена, приоритет, списки.
- Автоматическая периодическая проверка цен и хранение истории.
- Алерты о достижении целевой цены и о снижении цены (приложение, email, Telegram).
- Лента «Скидки» с сортировкой по размеру снижения и пометкой подозрительных скидок.
- Планировщик: рекомендация «купить сейчас / подождать», календарь распродаж, график цены.
- План покупок на месяц под заданный бюджет.
- Администрирование календаря распродаж и адаптеров магазинов.

### 2.3 Ограничения продукта

- Серверная часть должна быть написана на Java 21 с использованием Spring Boot (обязательное, по заданию курса).
- Данные должны храниться в реляционной БД PostgreSQL 16 (предпочтительное).
- Система должна получать цены только из публичных страниц магазинов без обхода защиты и без авторизации в магазине (обязательное, см. REQ-COMP-001).
- Система должна работать на сервере с 2 vCPU и 2 ГБ ОЗУ (внутреннее ограничение бюджета, см. раздел 3.5.7).
- Интерфейс должен быть на русском языке, цены — в белорусских рублях (BYN) по умолчанию.

### 2.4 Характеристики пользователей

| Класс | Описание | Частота и цели |
|---|---|---|
| Покупатель | Обычный пользователь интернета без технической подготовки; пользуется с телефона и компьютера | Несколько раз в неделю: добавить товар, посмотреть скидки, получить подсказку «покупать или ждать» |
| Охотник за скидками | Опытный пользователь, следит за 20–200 товарами, хочет видеть историю и график | Ежедневно: настройка порогов, анализ графиков, сводка скидок |
| Администратор | Владелец продукта | Редко: поддержка календаря распродаж, включение и отключение магазинов |

### 2.5 Допущения и зависимости

| Допущение / зависимость | Влияние, если не выполняется |
|---|---|
| Магазины публикуют цену в HTML или JSON-LD на публичной странице товара | Цена не извлекается; нужен специальный адаптер или магазин исключается из поддерживаемых |
| Вёрстка страниц магазинов меняется редко | Адаптеры перестают работать; требуется оперативное обновление (см. REQ-OBS-001, REQ-REL-001) |
| Доступен SMTP-сервер и Telegram Bot API | Алерты доставляются только в приложении |
| Для рекомендации накоплено не менее 14 дней истории | До этого срока выводится «Недостаточно данных» |
| Календарь распродаж актуален | Рекомендация «Подождать» по событию может быть неточной |

| 0.2 | INT-002, 008; FUNC-007, 010, 017, 022, 024; SEC-005; REL-003; OBS-001; MAINT-001 | Тёмная тема, Telegram, лента скидок, план покупок, администрирование |

## 3. Требования

Формат идентификатора: REQ-[ОБЛАСТЬ]-[NNN]. Приоритет: M — обязательно, S — желательно, C — возможно. Метод верификации по умолчанию — «Тест»; иные методы указаны в разделе 4.

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательские интерфейсы

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| REQ-INT-001 | Система должна предоставлять web-интерфейс на русском языке с адаптивной вёрсткой для ширины окна от 360 до 1920 px. | M | При ширине 360, 768, 1366 и 1920 px нет горизонтальной прокрутки, все элементы управления доступны. |
| REQ-INT-002 | Система должна поддерживать светлую и тёмную темы оформления, переключаемые вручную, а по умолчанию определяемые настройкой ОС (prefers-color-scheme). | S | Выбранная тема сохраняется после перезагрузки страницы; контраст основного текста не ниже 4,5:1 (WCAG 2.1 AA). |
| REQ-INT-003 | Система должна содержать три основных раздела: «Вишлист», «Скидки», «Настройки», доступных из верхнего меню. | M | Переход в любой раздел выполняется одним кликом с любого экрана приложения. |
| REQ-INT-004 | Система должна показывать понятные состояния «пусто» и «ошибка»: при пустом вишлисте — подсказку и кнопку «Добавить товар», при ошибке — сообщение на русском языке с причиной. | M | У нового пользователя на экране «Вишлист» отображается подсказка и кнопка; при сбое сервера пользователь видит сообщение, а не технический стек-трейс. |

#### 3.1.2 Аппаратные интерфейсы

Не применимо: система не взаимодействует с аппаратурой напрямую.

#### 3.1.3 Программные интерфейсы

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| REQ-INT-005 | Система должна получать название, изображение, цену и наличие товара со страницы магазина по HTTP(S), используя микроразметку schema.org (JSON-LD) или адаптер конкретного магазина. | M | Для каждого из 3 поддерживаемых магазинов цена корректно извлекается не менее чем на 95 % страниц из тестового набора в 30 страниц. |
| REQ-INT-006 | Система должна предоставлять REST API в формате JSON, описанное спецификацией OpenAPI 3.0. | M | Спецификация доступна по адресу /v3/api-docs и проходит валидацию без ошибок; все операции UI выполнимы через API. |
| REQ-INT-007 | Система должна отправлять email-уведомления через SMTP с шифрованием STARTTLS/TLS. | M | Тестовое письмо доставляется на реальный почтовый ящик не позднее чем через 60 с после события. |
| REQ-INT-008 | Система должна отправлять уведомления в Telegram через Bot API после привязки аккаунта пользователем. | S | После привязки по одноразовому коду уведомление приходит в чат пользователя не позднее чем через 30 с. |

### 3.2 Функциональные требования

##### Учётная запись

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| REQ-FUNC-001 | Система должна позволять регистрироваться по адресу электронной почты и паролю (не менее 8 символов, буква и цифра) с подтверждением адреса ссылкой из письма. | M | Без подтверждения почты уведомления не отправляются; повторная регистрация того же адреса отклоняется; слабый пароль отклоняется. |
| REQ-FUNC-002 | Система должна позволять входить в систему и выходить из неё; сессия должна действовать не более 7 суток. | M | После выхода защищённые страницы недоступны; по истечении 7 суток требуется повторный вход. |

##### Управление вишлистом

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| REQ-FUNC-003 | Система должна добавлять товар по ссылке на страницу магазина, автоматически определяя название, изображение, текущую цену и магазин. | M | После вставки ссылки поддерживаемого магазина поля заполняются не более чем за 10 с; добавление выполняется не более чем за 2 действия (вставить ссылку, нажать «Добавить»). |
| REQ-FUNC-004 | Система должна отклонять ссылку на неподдерживаемый магазин и показывать список поддерживаемых магазинов. | M | При вводе ссылки неподдерживаемого домена товар не создаётся, выводится сообщение «Магазин не поддерживается» и список магазинов. |
| REQ-FUNC-005 | Система должна позволять изменять целевую цену, приоритет (высокий, средний, низкий) и заметку к товару. | M | Изменения видны после обновления страницы; целевая цена должна быть положительным числом с точностью до 2 знаков. |
| REQ-FUNC-006 | Система должна позволять удалять и архивировать товар; архивный товар не должен проверяться. | M | Удалённый товар исчезает из списков; архивный товар не появляется в журнале проверок и не создаёт алертов. |
| REQ-FUNC-007 | Система должна позволять группировать товары по именованным спискам (например, «Ноутбук», «Подарки»). | S | Пользователь может создать до 20 списков и перенести товар между ними; фильтр по списку работает на экранах «Вишлист» и «Скидки». |

##### Отслеживание цен

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| REQ-FUNC-008 | Система должна периодически проверять цену каждого активного товара; интервал по умолчанию — 6 часов, настраивается пользователем от 1 до 24 часов. | M | По журналу интервал между проверками одного товара равен заданному ±5 мин. |

| ID | Требование | Приоритет | Критерий приёмки |
|---|---|---|---|
| REQ-FUNC-024 | Система должна позволять администратору редактировать календарь распродаж и включать/отключать адаптеры магазинов. | S | После отключения адаптера товары этого магазина не проверяются; добавленное событие календаря учитывается в рекомендациях. |

Правила расчёта рекомендации (REQ-FUNC-019). Для товара берётся история за последние 90 дней: min90 — минимум, med90 — медиана; trend — наклон линейной регрессии цены за 14 дней в процентах за неделю. 1) если истории меньше 14 дней или замеров меньше 5 — «Недостаточно данных»; 2) если текущая цена не выше 1,05 × min90 — «Купить сейчас»; 3) иначе, если trend ≤ −1 % в неделю, либо ближайшее событие календаря наступает в течение 30 дней, а текущая цена выше med90 — «Подождать»; 4) иначе — «Нейтрально». Недетерминированные и обучаемые компоненты не используются.

#### 3.5.3 Распределение

Система разворачивается как один экземпляр приложения и одна БД; географическое распределение и горизонтальное масштабирование в текущем релизе не требуются.

|---|---|---|---|

#### 3.5.5 Повторное использование

Модуль расчёта рекомендаций должен быть независим от web-слоя и хранилища, чтобы его можно было использовать повторно (например, в мобильном клиенте).

#### 3.5.6 Переносимость

Система должна работать на любой ОС, где есть Docker или JDK 21; зависимость от конкретного облачного провайдера не допускается.

#### 3.5.7 Стоимость

Разработка и размещение не должны требовать затрат: используется бесплатное ПО и ресурсы учебной инфраструктуры или бесплатный тариф хостинга (0 BYN на лицензии и сервисы).

#### 3.5.8 Сроки

Сроки определяются графиком курса «Жизненный цикл разработки ПО»: SRS (лабораторная работа № 3) — октябрь 2026; MVP 0.1 — по графику следующих лабораторных работ; точные даты уточняются у преподавателя.

#### 3.5.9 Доказательство концепции

До полной реализации необходим прототип извлечения цен: цель — проверить, что цена и наличие извлекаются со страниц 3 магазинов (по 10 страниц) не менее чем в 95 % случаев (REQ-INT-005); результат определит состав поддерживаемых магазинов и необходимость специальных адаптеров.

#### 3.5.10 Управление изменениями

Работа ведётся в ветках git с обязательным pull-request и ревью; версии нумеруются по SemVer; изменения фиксируются в CHANGELOG.md; изменение требования увеличивает суффикс версии идентификатора и записывается в историю изменений.

### 3.6 ИИ/МО

Не применимо: рекомендация по времени покупки вычисляется детерминированными статистическими правилами (REQ-FUNC-019) и не использует обучаемые модели. Если в будущем будет добавлена модель прогнозирования цены, этот раздел будет заполнен.
